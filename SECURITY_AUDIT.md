**Local reproduction (2026-10-11):** on the maintainer's Windows machine running
Kaspersky (`avp.exe`; Microsoft Defender disabled), the legitimate build script
itself — `apps/desktop/scripts/build-sidecar.mjs`, which assembles the engine
bundle — was silently terminated **3 out of 3 runs** at the point where it
copies the Playwright payload and is about to download/write the portable
`node.exe`; on the first run the script file was additionally removed from disk
(presumed File-Antivirus quarantine). There was no JavaScript exception and no
stderr output — an external process kill. No exclusions, renames, packing or
other evasions were applied; the script was re-authored from the maintainer's
own source and re-verified by lint/tests, and the real installer build was
moved to clean GitHub CI runners.

`PDM:*` detections come from Kaspersky's behavioral engine (System Watcher),
not from an exact file signature. That is consistent with either (a) heuristics
flagging an unsigned installer that unpacks a runtime and launches a child
process, or (b) genuine malicious behavior we have not observed. The distinction
requires the vendor's analysis — see §6 and §7. The local reproduction above is
direct evidence that Kaspersky's behavioral monitor terminates **benign**
MadScope build tooling that downloads a runtime, which supports hypothesis (a)
for the installer detection as well — it is evidence, not proof, and belongs in
the vendor submission.

- Release workflow run `37985200086` (event: tag push), Windows job `114005348193`,

- The GitHub server-side SHA-256 digest of each release asset **exactly matches**
  the published `CHECKSUMS.txt`, which was generated by `sha256sum` inside the
  release job itself. Assets were uploaded by `github-actions[bot]`.
- All build downloads came from official sources; WiX, NSIS and the Tauri NSIS
  utils were hash-validated by the Tauri bundler itself during the build.

Integrity (the file is what our pipeline produced) is **not** safety (the file
contains nothing malicious). A compromised npm crate, Rust crate or CDN payload
at build time would not be visible to source inspection; the chain above bounds
that risk (lockfiles, official sources, hash validation where the tooling
supports it) but does not eliminate it.

## 5. Potential risks (documented, deliberately not changed)

- **R1 — Behavioral resemblance.** The app legitimately ships a portable
  `node.exe` and executes a large bundled JavaScript file, and NSIS
  self-extractors are a classic heuristic trigger. This pattern is
  indistinguishable at the heuristic layer from Node-based loaders. Inherent to
  the architecture; code signing (§8) is the practical mitigation.
  **Reproduced locally on 2026-10-11** (see §1): Kaspersky terminated the
  benign build script that downloads the runtime — same pattern, no malware.
- **R2 — `/api/diff` accepts absolute file paths.** By design for the local
  compare feature; the server is loopback-only, so exposure is limited to local
  processes. Hardening (confining reads to the app data dir) needs UI testing —
  follow-up, not changed here.
- **R3 — Playwright browser payloads are TLS-verified only.** Playwright 1.64.0
  publishes no per-browser checksums; there is nothing independent to pin.
  Mitigated by the new SHA-256 inventory (audit trail of exactly what shipped).
- **R4 — Tauri `csp: null`.** The desktop UI has no Content-Security-Policy.
  Recommended hardening, but it must be tested inside the real WebView before
  shipping — deliberately not changed in this pass.
- **R5 — 14 dev-tool advisories remain** (vitest/vite/tailwindcss chains; 3
  critical). They affect development machines and CI only, never the shipped
  installer. Upgrading means vitest 5 / vite 8 / tailwind 4 major migrations —
  scheduled follow-up, not forced here.
- **R6 — Mutable-tag pinning drift.** Pinned SHAs do not auto-update; refresh
  periodically (Dependabot for github-actions is recommended).

## 7. False-positive submission procedure (Kaspersky)

1. Collect: the exact file that was detected (MSI and/or setup.exe), its
   SHA-256 (§1), the detection name, the Kaspersky product + database version,
   and the event date/time from the report.
2. Submit the file for free analysis at **Opentip**:
   <https://opentip.kaspersky.com/> (upload the installer; record the verdict
   URL here).
3. Additionally open a **false-positive report** at
   <https://support.kaspersky.com/abuse> (choose "False detection"), attaching:
   - both installers and their SHA-256 hashes,
   - a link to this repository and to release v1.1.0,
   - the provenance summary from §2 (tag → commit → run → logs → checksums),
   - a statement that the binaries are unsigned (why heuristics fire) and that
     the app only renders pages locally via a bundled engine.
4. Record the ticket number and the vendor's response in the table in §1.
5. Do **not** delete, replace or re-publish release assets in response to a
   detection without owner approval.

## 8. Code signing — options for the owner (manual step)

Unsigned binaries carry zero reputation and are the single largest heuristic
factor here. Reputable options (no self-signed certificates, ever, for public
distribution; keys must never be committed to this repository):

| Option                                 | Notes                                                                                                                 |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **SignPath.io** (open-source program)  | Free code signing for OSS via the GitHub integration; public certificate, best reputation-per-effort for this project |
| **Certum Open Source Code Signing**    | Free EV-backed signing for open-source developers (requires qualified certificate issuance)                           |
| **Azure Trusted Signing**              | Paid; requires an org identity verified by Microsoft; good SmartScreen reputation path                                |
| **SSL.com / DigiCert / Sectigo OV-EV** | Traditional code-signing certificates; EV gives the fastest SmartScreen reputation                                    |

Where secrets would live if/when signing is wired in: GitHub Actions secrets
referenced explicitly from the release workflow (e.g. `WINDOWS_SIGNING_CERT`);
the workflow change is a follow-up owned by the maintainer after the
certificate exists. Timestamping must be enabled so signatures outlive certs.
